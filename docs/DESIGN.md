# 设计说明与规则出处

> 这份文档解释**为什么这样设计**，以及规则库里的说法从哪来、可信度如何。
> 供想改规则、或想判断「这条能不能信」的人参考。

## 一、为什么是「注入卡片」而不是纯提示词

市面上的提示词插件通常给一段 system prompt，让用户自己粘贴。
问题有三个：

1. 每次新对话都要重新粘
2. 用户改了一版，旧版还在别处
3. 无法和工具联动（没法让模型「先查库再写」）

Cordis 的 `systemPrompt.section()` 解决了 1 和 3：
卡片每次会话开始时自动组装，且能通过工具读写库。

**代价**：卡片占每一轮的上下文。所以卡片必须短——
只放「不查也知道该怎么做」的行为约束，题材细节全在 `rules/`。

## 二、为什么卡片要注册两个宿主

`systemPrompt.section()` 在插件自己的 ctx 上注册时，段落在插件作用域内。
委派出来的子会话可能看不到这个作用域。

所以 `registerSection()` 会尝试同时注册到：
- `ctx.systemPrompt.ctx`（服务所属的宿主 ctx）
- `ctx`（插件自己的 ctx）

任一处成功即可，重复注册会命中 `already registered` 而被静默跳过。
这与社区里其他插件的通行做法一致。

## 三、为什么 `language` 只管卡片与自检，不管规则库

卡片与自检文案是**代码生成的**，可以按语言切换。
`seed/rules/` 是**文件内容**，由用户/维护者撰写，强行翻译会失真。

所以：`language: 'en'` 时，卡片和 `promptlib_check` 的输出变英文；
`rules/` 里是什么语言就还是什么语言。想全英文，就自己换掉 `seed/rules/`。

## 四、为什么 `promptlib_finalize` 默认不删

删文件不可逆。这类工具最容易出的问题是「自动化得太彻底」——
用户说「好了」，工具顺手把中间版全清了，结果发现最终版挑错了。

所以设计成两段式：

```
第一次调用（不传 confirm）→ 只预演，列出将删清单
用户看到清单并同意 → 第二次调用（confirm: true）→ 真删
```

删除范围另加三重限制：
1. 只在 `workspace/<任务名>/` 内
2. 只删形如 `vN.md` 的文件
3. `keep` 必须是已存在的版本文件

## 五、为什么不做平台适配

一开始考虑过：按 Midjourney / FLUX / SD 分别改写提示词。
放弃了，原因：

1. **掩盖错误**。用户写 `--ar 3:2` 又说是 FLUX，自动删掉参数会让他以为平台支持
2. **版本会过期**。参数取值范围随模型版本变，写死就是埋雷
3. **收益低**。真正影响出图的是构图/光/材质，不是参数拼写

现在的做法是：**只说清哪条语法属于哪个模型**，让模型自己判断要不要加。
`promptlib_check` 会抓「语法与模型不匹配」。

## 六、为什么不做向量检索

库是给人读的 Markdown，通常几十到几百个文件。
向量检索需要 embedding 服务或本地模型，会带来：
- 额外依赖
- 额外的网络/算力成本
- 索引与内容不同步的问题

现在用的是「分段 + 覆盖率打分」：

```
分数 = 查询词被该段覆盖的比例 × 0.7 + Jaccard × 0.3
```

用覆盖率而不是纯 Jaccard 的原因：长段落词多，纯 Jaccard 会把它稀释；
短查询也容易被整篇全文淹没。分段后取最高分，两个问题一起解决。

实测：查「拿铁 咖啡 陶杯 窗光」能命中 0.71 的相关段落。

## 七、规则的可信度分级

沿用原素材的标注习惯：

| 标签 | 含义 | 能怎么用 |
|---|---|---|
| **A** | 官方文档原文 | 可以直接当规则 |
| **B** | 官方内容，但经第三方转述 | 可以当规则，注明「转述」 |
| **C** | 第三方文章 / 社区实测 | **只能当假设**，需自己验证 |
| **D** | 综合推断，未验证 | 只能当线索，不要写进规则 |

**把 D 当 A 用是这类工具最大的坑。**

## 八、规则库的来源构成

初版规则库来自四条线：

1. **主流模型官方文档**（A）
   OpenAI 图像生成/提示指南、Midjourney Prompt Basics（部分）、
   BFL FLUX Prompting Guide 总览、Stability SD3.5 Prompt Guide、Google Imagen 指南

2. **公开教程与社区实测**（C）
   摄影向的提示词写法、运镜教程、产品图避坑帖

3. **实践反馈**（C/D，来自实际出图踩坑）
   发丝光环、逆光放射光柱、浅景深拍手指糊、转头重画脸等

4. **方法论合并**
   六层框架、通用公式、七块结构三套说法合并为一套

## 九、已知的规则争议

这些地方素材之间说法不一致，当前处理如下：

| 争议 | 当前取舍 | 理由 |
|---|---|---|
| `pore-level skin texture` 是否比 `detailed skin` 有效 | **C 级，未证实** | 首轮 A/B 实测 2:2 无差异，疑为测试设计的天花板效应 |
| 镜头参数是否物理真实 | **只是外观线索** | OpenAI 官方明确说明 |
| 十六进制色值是否准 | **只是强引导** | 社区实测有偏差 |
| Midjourney 版本号 | **规则里不写版本号** | 会过期 |
| `--style raw` 是否必须 | **建议，非强制** | 参数取值未在官方页核实 |

## 十、性能取舍

| 地方 | 做法 | 原因 |
|---|---|---|
| 卡片长度 | 软上限 8000 字符（实际 1.6 K） | 每轮都占上下文 |
| 检索文件数 | 默认 400，可配 | 防止大库拖慢 |
| 单文件大小 | 跳过 >512 KB | 索引是给规则/样本用的，不是给大素材 |
| 读文件 | 默认 400 行，上限 1200 | 让模型自己分段读，而不是一次灌满 |
| 目录深度 | 最多 4 层 | 防止意外扫到 node_modules 之类的深树 |

## 十一、扩展点

想加东西时改哪里：

| 想加 | 改哪 |
|---|---|
| 自检规则 | `lib/constants.js` 加模式 + `lib/check.js` 加判断 + `lib/i18n.js` 加文案 + 测试 |
| 题材母版 | 往 `seed/rules/` 写 Markdown |
| 卡片内容 | `lib/card.js`（注意长度） |
| 新语言 | `lib/i18n.js` 加一张表 |
| 新工具 | `index.js` 里 `ctx.tools.register`，重逻辑放 `lib/` |
